BCD Travel needs to expose Genie-powered analytics to ~10,000 external users across 1,000+ customers, each seeing only their own data.

BCD-Specific Context

  • External users via Azure AD B2C — users never see Databricks
  • Current approach: non-deterministic function + prompt-based isolation (fragile)
  • Advito (sister org, ~600 users) shares same account, different workspace
  • Custom claims (current_oauth_custom_identity_claims()) support on Genie surface is under active escalation

Three Patterns

Pattern B: Shared SP + Custom Claims

Single Service Principal for all clients. Tenant isolation via custom_claim in OAuth token. UC row filters enforce at query time.

  • O(1) operational overhead
  • Scales to millions of tenants
  • Onboarding = 1 DB insert
  • Genie surface support unverified
  • Single SP = shared blast radius

Pattern A: SP-per-Client

Each customer gets a dedicated Service Principal. RLS via session_user() mapped to tenant ID.

  • Works today — no Genie gap
  • Per-client compute attribution
  • Blast radius per SP
  • O(N) SP management overhead
  • 5,000 SPs to manage
  • Secret rotation at scale

Pattern C: User Provisioning (SCIM)

Provision each external user as a Databricks user. Native identity-based access control.

  • Native Databricks identity
  • Full audit per user
  • 10K users = licensing + provisioning burden
  • External users in Databricks platform
  • Only viable for Advito (600 internal users)

Pattern A: SP-per-Client

Each customer gets a dedicated Databricks Service Principal. Data isolation via session_user().

How It Works

  1. Client authenticates with Proxy via API key
  2. Proxy looks up which SP belongs to this client (from Lakebase registry)
  3. Proxy gets OAuth token for that specific SP
  4. Proxy calls Genie API with the SP's token
  5. Genie executes SQL → UC sees session_user() = SP-A's app_id
  6. Row filter/dynamic view joins SP app_id → tenant_id, returns only that tenant's rows

BCD Context: VJ's Concern is Valid

VJ raised that managing ~5,000 SPs is a significant operational burden. This is correct — it's essentially a service to build, not a script. However, Ibotta runs 1,300+ SPs as precedent. This pattern works today without waiting for custom claims on Genie.

Pattern B: Shared SP + Custom Claims

Single Service Principal for all clients. Per-tenant isolation via custom_claim in the OAuth token.

How It Works

  1. Client authenticates with Proxy via API key
  2. Proxy resolves client → tenant_id from Lakebase registry
  3. Proxy gets OAuth token from the single shared SP with custom_claim=tenant_id
  4. Proxy calls Genie API with the claims-bearing token
  5. Genie executes SQL → UC reads current_oauth_custom_identity_claims()
  6. Row filter returns only rows where tenant_id matches the claim

Blocker: Genie Surface Validation

current_oauth_custom_identity_claims() works for JDBC and SQL Execution API. Genie Conversation API support is under active escalation (Q2 priority, 17 use cases, 12 accounts, BCD named). Must verify before committing to this pattern.

Pattern C: User Provisioning (SCIM)

Provision external users directly as Databricks users. Native identity-based access.

When This Makes Sense

  • Advito (~600 users): Internal users, AWS Cognito auth, SCIM provisioning is the clear path
  • BCD (10K users): External users via Azure AD B2C — too many users, licensing burden, users never need to see Databricks

Recommended Strategy

Phase 1: Start with Pattern A (Now)

Deploy SP-per-client for the April pilot. Works today, proven at scale (Ibotta runs 1,300+ SPs). Build the SP lifecycle automation as a service.

Phase 2: Migrate to Pattern B (When Ready)

Once custom claims are validated on Genie surface (Q2 escalation), migrate to shared SP. The proxy architecture is the same — only the token minting changes.

Advito: Pattern C (Parallel)

Advito's 600 internal users are a clean SCIM provisioning case. Run this in parallel — different workspace, different auth (AWS Cognito).

Key Questions for Your Team

1. Custom Claims Timeline

When will current_oauth_custom_identity_claims() be validated on the Genie surface? This determines if we start with A or go straight to B.

2. SP Management Appetite

Is VJ's team willing to build and operate an SP lifecycle service (provisioning, rotation, offboarding) for 1,000+ SPs? If not, we need to push harder on custom claims.

3. April Pilot Scope

How many tenants in the pilot? If <50, Pattern A is trivial. If hundreds, the management burden starts immediately.

4. Advito Timeline

Is Advito's SCIM provisioning (Pattern C) independent? Can it proceed in parallel with BCD's proxy architecture?

5. Rate Limit Strategy

5 questions/min/workspace. With 1,000+ clients, do we need multi-workspace round-robin from day one, or is pilot volume manageable?

6. Security Review

Pattern B's single SP has access to all tenant data (row filter is the boundary). Does BCD's security team need per-SP isolation (Pattern A)?
